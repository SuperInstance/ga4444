# gt4444.c -- Gale's game, exact, and the table is COMPLETE

Single self-contained C11 program, no dependencies, no libraries beyond libc.
Integer-only arithmetic, so the output is bit-identical on any machine.

    make            # build ./gt4444
    make selftest   # board + value-encoding + primitive checks, no solving
    make export     # checks, known-answer check, then the complete export

**9,067,975 positions** — every legal non-terminal position of 4x4 four-in-a-row
at every ply 0..16. Not a sample, not a ply bound: the whole game, because the
whole game fits in 52 seconds on one core.

## The one check that fails, and why it is the task that is wrong

The task states the known answer is **"first player wins"**. This solver
measures **0 — a draw**. Three independent computations agree:

1. the production solver (bitboard negamax + alpha-beta + TT), 202,160 nodes;
2. the same search with **no transposition table and no threat shortcut** —
   plain negamax + alpha-beta straight from the rules — 40,152,637 nodes;
3. an independent **Python** negamax + alpha-beta written from the rules with
   no tables and no shortcuts at all, 30,319,885 nodes.

Three different implementations, two of them with every optimisation removed,
all returning 0. The program prints the failure and exits non-zero; it does not
convert the disagreement into a pass.

The last one is the important one, and it is the reason it exists.

## Why there is a Bellman check at all

Three separate solver bugs got through the other checks, because **the other
checks compare solver variants against each other, and every variant shared the
bug.** Cross-validation is blind to a common-mode error.

1. `can_win_next(opponent) → return LOSS(1)`. Unsound: the threatened square can
   simply be *blocked*. It was in the production solver, the pruning-disabled
   solver and the TT-free solver simultaneously.
2. `mirror()` did not add a half-move for the move into the child, so every
   distance-to-win was off by one per level of recursion. Signs often survived
   by luck; distances did not.
3. The child call passed `occ ^ cur ^ bit`, handing the stone just played to
   the **opponent**. Every value in the table was wrong. This one also made
   the search ~113× slower (40,152,637 → 202,160 nodes on the empty board),
   because the opponent always appeared to hold a free stone.

What caught them was checking the table against **the rules of the game**:

    value(P) = max over moves m of ( m wins immediately ? +1 : −value(P after m) )

Every child's value is in the table, because the table is complete and the game
tree is closed under it. So this is a check of the whole table, not a sample.
It found 4,572,569 violations before bug 3 was fixed and 0 after.

That check is cheap, and it is the reason this table can be trusted at all.
It has been back-ported to `../connect4/ctool.c`.

## Two things that are easy to get wrong in the representation

- **A column's colours are not constrained.** There is no gravity, and any empty
  cell may be played, so a column may read `X O O X`. An earlier revision of
  the enumerator assumed a column alternates — true of tic-tac-toe-style
  placement games, false here — and silently dropped half the positions
  (ply 2 came out at 56 instead of 49).
- **`cur + occ` is not injective here.** With `occ = 0b01, cur = 0b01` the sum
  is `0b10`, which is also `occ = 0b10, cur = 0`. That trick is sound for
  Connect 4, where the per-column values are disjoint ranges, and unsound here.
  The key is the explicit pair `occ<<16 | cur`.

## Conventions (also in every export file's header, and in the manifest)

- **value** is the game-theoretic value **for the side to move**: `+1` wins,
  `0` draws, `−1` loses. This table covers every ply, so the side to move
  alternates — P0 at even plies, P1 at odd plies. The ply is
  `popcount(p0|p1)`, so a reader recovers it from the boards. The P0-perspective
  value is `value` on even plies and `−value` on odd plies.
- **horizon: none.** The board is 16 cells, so the search always reaches the
  end of the game. Every row is exact.
- **legality**: the game has not already ended — neither side has four in a row
  and the board is not full. Terminal positions are excluded and counted in the
  manifest (`terminal` column).
- **order**: lexicographic in the first cell-index sequence that reaches the
  position, cells 0..15 row-major from the top left, deduplicated on the
  position. Determined by the board alone.
- **line format**: exactly three decimal fields, `p0 p1 value`, newline
  terminated. `#` lines carry the conventions. No fourth column.
- **digest**: FNV-1a 64, hand-rolled, over the exact ASCII bytes of every data
  line of every ply file in ply order, terminating newlines included, `#` lines
  excluded.

## Five in a row

Five in a row is **impossible** on a 4x4 grid — the longest line, row, column
or diagonal, is 4 cells, so a five-in-a-row game on a 4x4 board cannot end in a
win at all. The solved game is `m,n,k = 4,4,4`, four in a row, Gale's game. The
export header says so on every line of every file, because the seed for this
rung proposed 5x5 five-in-a-row and that correction is easy to lose.
